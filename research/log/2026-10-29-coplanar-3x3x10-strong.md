# 2026-10-29: 3×3×10 共面4点禁止盤の強解決（K0575）

研究ログ雛形（research/log/README.md 準拠）。

## 背景

共面4点禁止家族（K0529）の強解決は m=9 まで完了していた（K0569〜K0574）。enum3 のディスク方式は m=10（90点・約6.5億局面）にも届く設計だったが、ソース側の配列が81点で固定されていたため、まず拡張して回帰を通し、次に本計算・順序照合・サブツリー検証・軌道数え上げまでを一晩で完了させた。

## やったこと

- enum3.cpp / dfs_sub.cpp の局面表現配列を 81 点から 99 点（m≤11）へ拡張し、拡張後のバイナリで m=7 を再計算して保存済み結果とバイト一致を確認した。
- 禁止4点組数を Python の Leibniz 行列式で数え、327,602 を得た。
- enum3 で m=10 を順序0 (x,y,z) で生成・評価し、上位層ダンプを得た（約49分）。順序1 (z,y,x) でも生成・評価し、出力のバイト一致を確認した。
- 外積DFS（dfs_sub）で初手代表3種（角・中央・辺中点）のサブツリーを独立に解いた。角と中央は enum3 評価と並行実行で完走し、辺中点は並行実行時にメモリ競合で強制終了したため、enum3 終了後に単独で再実行して完走させた。
- 最大層 12,122,096 配置の軌道数え上げは orbits_top.py では処理が終わらなかったため、同一の群作用・正準代表・JSON 形式を持つ C++ 移植 orbits_cpp.cpp を書き、m=9 のダンプから orbits_m9.json をバイト一致で再現して検証したうえで m=10 に適用した。
- 知識項目 K0575 を追加し、実験 README と results.md を m=10 まで拡張した。

## 結果

有限計算として次を確認した。

- 禁止4点組 327,602、安全局面 649,610,028、K=9、s=3（K0529 と整合）。
- 空盤 (g,h)=(2,2)。最大 nimber は g/h とも 5（m=9 から据え置き）。
- 初手は角40点 (0,1) と中央10点 (0,0) が勝ち、辺中点40点 (1,0) は全て負け、z 層で一様。
- 最大配置は 758,029 軌道（サイズ {8: 796, 16: 757,233}）。m=9 にあったサイズ4の軌道は消えた。
- orbits_m10.json は 21,982,584 バイト（SHA-256 0a674a3092270ae27e9e644b26e32f9d5689efc34aef07bc59a483a1e1a09bdd）。

## 検証

- enum3 の順序0/順序1 出力はバイト一致（statehash xor=95f5c318f6491045、sum=d96c3fe53db4941b）。
- 禁止組数は Leibniz C++（enum3）・外積 C++（dfs_sub）・Python の3方式で一致。
- dfs_sub の3サブツリー解が enum3 の初手表と一致（訪問局面数 51,984,234 / 52,482,190 / 63,793,592）。
- orbits_cpp.cpp は m=9 で保存済み JSON をバイト一致で再現。
- 層別局面数の合計が総局面数と一致し、軌道サイズの合計が最大層数と一致。

## 残課題

- m≥11 の Grundy は未解決。m=11 は約15億局面と見積もられ、現行 enum3 の評価メモリ（現在層の32ビット累積配列 約5.6GB＋諸配列）では上限を超える。累積配列を16ビット化し hasLegal をビットセット化した改修版は手元で作成し、m=8 の回帰（シャード分割経路を含む条件でも保存済み結果とバイト一致）まで確認済みだが、repo への統合と m=11 の実行はこれからである。
- 一般 m に対する g(∅)=2 や型別初手パターンの証明は未着手（有限範囲の観察に留まる）。
