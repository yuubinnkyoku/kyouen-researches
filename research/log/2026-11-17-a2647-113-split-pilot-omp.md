## 3. 段会計の修正（W36 §3.2/§4.1 の誤り）

### 3.1 CaDiCaL に再開は無い

W30 §3.3/W23 §3.1 の通り native CaDiCaL 3.0.1 に checkpoint/resume 機能は無く、
`-c` を変えて再実行すれば学習は消え、常にゼロからになる。
W36 §3.2 の「枝内段階ラダー（5M×7 ≒ 35M）」は、各段を独立 fresh run とするなら
**各段が段番号に比例する再実行コストを含む**。W36 が「ほぼ 105M で足りる」と
見積もった根拠がここで崩れる。

### 3.2 決定的なのですべての再実行が同じ結果になる（実測）

`determinism/` 記録: sub0.cnf（SHA `ad01c541…`）を `-c 100000` で2回実行:
run1/run2 の proof SHA-256 が2回とも
`810af2633a890ccc3d963aedf0aba3bc242a26d6082e53a55b48d649e3e0d16a`
（byte-identical）、かつ W36 §5.1 の pilot `p0.drat`（同じ入力・同じ予算、別時刻）とも
同一。つまり native CaDiCaL 3.0.1 は入力+予算に対し決定的。
**同額段の再実行は新しい情報を一切生まない**。ラダーは厳密な増予算でなければ意味がなく、
消費総数はΣ(段予算) ではなく最終段の累積「理論到達点」ではない実行 conflicts 総和になる。

### 3.3 増予算ラダーの設計

1枝あたり次の4段とする: `5M → 10M → 20M → 35M`。
CaDiCaL の conflict 上限である 35M は W36 の枝均等配分と同じ到達点。消費総数（1枝）:
5+10+20+35 = **70M conflicts**。3枝合計 **210M**。
段の費用（実測 cps 1,208〜2,869 の幅を使う。枝2 の保守 1,208 で35M 段: ≈29,000 s ≈ 8 h
`[INFERENCE]`。枝0 の楽観 2,869 で35M 段: ≈12,200 s ≈ 3.4 h `[INFERENCE]`）。
1段が VM の窓（≈2 h、時に40分）を超える場合、その段は再起動のたびに最初からに
なり、**最後の段ほど空振りコストが大きい**。これが§6 の中止基準に直結する。

## 4. 健全性の具体化: なぜ各サブ UNSAT が全体 UNSAT か、領収書をどう構成するか

### 4.1 推論の骨格（W36 §2.2 の再定式化）

被覆（§1.3）: 任意の割当 α ∈ {0,1}^{17,180} に対し、α が満たす枝がちょうど1つ存在する。
（ちょうど1つであることは C1 で確認済み。）

したがって: F が充足可能なら、あるモデル α があり、α の (v15847, v15868) 成分に応じて
ちょうど1つの枝 t_k が満たされ、そのとき F ∧ units(t_k) は α で充足される、すなわち
**いずれかの枝が SAT**。対偶: **全枝 UNSAT ⇒ F UNSAT**。SAT 側の停止も同型:
いずれかの枝で SAT を出せば F SAT（§6）。

この推論は枝の証明系に全く依存しない（各枝が F ∧ units(t_k) という有限CNFへの
有限反駁であることのみ必要）。多元的依存や学習の共有は不要。これが監査容易性の核。

### 4.2 仮定ベース UNSAT が独立 DRAT にならない点（W36 §2.1 の再確認と補強）

assumption/restart による in-process 分割では、仮定下 UNSAT の証明は
「F ∧ assume ⊢ ⊥」の導出を含み、**そのままの DRAT 連鎖は F 単独では検証できない**。
pysat Cadical195 はさらに (a) 証明を RAM に全読込（W30 §0）、(b) incr 非対応、の
実装上の制約も持つ。本作業でさらに構文的側面を実測した（`rat_check.py`）:

- 枝閉包節 C = ¬units(t_k) が F 上で **RAT** か（= 3枝証明が F 上の単一 DRAT 連鎖に
  合成可能か）を検査。v_a=15847 と衝突する F の節は2つ（clause 33004, 33005）。
  2 resolvents とも unit propagation で反駁できず（resolvent size 1 * 2）、
  **VERDICT: NOT RAT**（0.2 s）。
- つまり仮定どころか静的分割でも、枝を閉じる節は F への DRAT 追加として許されず、
  **3枝の証明は決して F 単独の単一 DRAT ファイルには合成できない**。
 どこを見ても「1本の巨大証明」は作れない。各枝の証明は枝の入力 CNF（F ∧ units(t_k)）
 に対する独立 DRAT として完結させるしかない。

### 4.3 領収書の構成（実装済み: `compose_receipt.py` → `receipt.json`）

R1〜R3（枝領収書）: 各枝、UNSAT と報告した段の proof.drat について
`drat-trim sub_k.cnf -i`（バイナリ DRAT なので `-i` 必須、W30 §5.3）が
`s VERIFIED` を出すこと。入力 sub CNF と proof の SHA-256 を
`audit-drat-trim.json` に記録（driver `verify` がこの形で書く）。

R4（被覆領収書）: §1.3 C2 の cover.cnf（F ∧ ¬t0 ∧ ¬t1 ∧ ¬t2、3節）
…ではなく変数対のみの3節 `(-15847)(15847 -15868)(15847 15868)` について
drat-trim `s VERIFIED`（入力 SHA `c33d3624…edb1381f`、proof SHA `5bcf3d2d…` 、0.135 s）。

R5（構造照合）: 各 sub_k.cnf の本体が F の本体と一致（§1.2）。
R6（凍結 SHA）: `sub-sha.json` 記載 SHA が solve 実行時の入力 SHA と一致
（driver が solve 前に毎回照合）。

R1..R3 ∧ R4 ∧ R5 ∧ R6 ⊢ F UNSAT。ただしどの枝もまだ UNSAT が出ていないため、
現時点の `receipt.json` の verdict は（定義通り）`incomplete`、全枝
`MISSING (no UNSAT stage)`。監査済み主張は本 log には一切含まれない。
（`1296 ≤ A(2647) ≤ 1322` は本作業で動いていない。）

### 4.4 合成の実証（縮小インスタンス）

`synth-verify/`: F_syn = `p cnf 17180 3`（`1 0` / `-1 0` / `15847 0`）を
sub0 = F_syn ∧ `(-15847 0)` として解いたもの: **UNSAT**、proof.drat.gz
（展開 10 B、SHA `2f87e4a5…adca9c3d`）、drat-trim は `c found complementary unit

まで含めて証明検証が通ることを**1件実証**した。2変数3枝相当の縮小合成
（F が `(1 2)(-1 2)(1 -2)` のようなSATнадtinyもの）も `receipt-demo/` で

### 6.2 再起動後の再開

再起動で殺された段は `solver.json` を持たない。`./full_run_113.sh start` を再実行
すれば、solver.json のある段は skip し、殺された段のみを最初から再実行する。
**失うのは常に「実行中の1段の進行中分」のみ**。これは W36 設計の再起動耐性の骨格
（§2.2 の「枝×プロセス」構造）がそのまま効いている点で、段会計の誤り（§3）とは独立に正しい。

ただし: 35M 段は最重枝で ≈8 h かかる `[INFERENCE]` ので、窓が2 h なら同一種で
3〜4回の空振りが予想される。brane: 35M 段を投入する前に 10M 段・20M 段の
実測 cps・drat-trim 検証可否（RAM）を見て、35M 段を 12M/23M の2段に割るか
そのまま行くかを決める（本 log の範囲外）。

## 7. 限界

- 1M パイロットは各枝1点のみ。cps の枝間比（2.4倍）と B/conflict の枝依存性
  (218.7〜266.7) が 10M/20M/35M 域で保たれる保証は無い `[INFERENCE]`。

  低い `[INFERENCE]`）。
