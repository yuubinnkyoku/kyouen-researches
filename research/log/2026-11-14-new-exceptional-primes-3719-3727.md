# 2026-11-14 既知4素数の外側で新たな等号不達成素数 p=3719, p=3727 を発見（証明書つき）

## 発見の順序

1. 等号達成の証人を浅く探す走査（`d = h..h-5` の6通り、各45秒）を 3701..3899 に延長した。
2. **p=3719 と p=3727 だけが「タイムアウト0で不達成」**だった。既知の4素数（2207・2531・
   2647・3251）はこの走査では毎回タイムアウトしており、挙動が違った。
3. p=3719 について `d = h..h-23` の24通りを追加で走査 → **全24個が短時間UNSAT**（281秒、
   タイムアウト0）。前の4素数と違って「難しいUNSAT」ではなく「易しいUNSAT」だった。
4. サイズ `h+2` は `(x,c,e) = (1,1,0)` の一クラスしかないので、**単一CNF**を直接解いた:
   - p=3719（h=1859, size=1861）: 13,012変数・105,940節 → **UNSAT 2.0秒**
   - p=3727（h=1863, size=1865）: 13,040変数・100,592節 → **UNSAT 20.7秒**
5. 両方について DRAT を作り、`drat_check_incremental.cpp`（K0707の削除健全性修正版）で検査:
   - 3719: 23,750行 → **VERIFIED**（31.6秒）
   - 3727: 334,667行 → **VERIFIED**（929秒）

## 結果

```
A(3719) <= 1860 = h+1
A(3727) <= 1864 = h+1
```

- 一般上界 `(p+3)/2` を1下回る。既知4素数と同じ「等号不達成」の形。
- ただし **`h+1` に届くかは未判定**（2207 は届き、2531・2647・3251 は届かない）。

## 方法的な副産物

- 等号判定は **1素数1CNF** で済む（サイズ `h+2` のクラスが一意なため）。従来の `d` ごとの
  全走査（`h` 個のCNF）は不要。
- UNSAT 側（不達成）は速く、SAT 側（達成）は遅い。よって「速いUNSATで候補を拾ってから
  証明書を付ける」国勢調査が実用的。`census_h2_single_cnf.py` がその道具。
- 既知4素数が 2003..3500 の範囲で見つかっていたため「4個で全部」という印象があったが、
  範囲外にさらに2個あった。**不達成素数の分布はまだ分かっていない**（K0101の問いのまま）。

- 8素数で `A(p) <= h`。いずれも h+1 の3クラスをすべて証明書つきで UNSAT にした。
- (1,1,1) クラスの難しさは素数ごとに大きく違う: 3719 は 150 秒で解けるが 3727 は
  3.68 GB の証明書になる。同じ「1クラス」でも探索木の形が全く違う。
- 既知4素数と合わせると、等号不達成 13 個のうち `A(p) <= h` が確定したのは

## 観察: 例外素数は「近接クラスタ」に現れる


- **これは記述的な観察であって主張ではない**。クラスタが偶然か、何か数論的な理由があるかは
  未検証。過去に剰余仮説（mod 8 / mod 12 / v2(p−1)）を試して有意でなかった経緯がある
  （置換検定 p=0.37/0.32 で撤回）ので、同じ轍を踏まないよう「見た目」以上のことは言わない。
- 検定するなら「不達成素数の間隔分布」を、同区間の素数全体から無作為抽出した間隔分布と
  比較する置換検定になる。標本が 14 個では検出力が低い。

## 事故: 同一ディレクトリへの並行証明書生成で receipt が壊れた

- 5059 の (0,1,0) クラスを、前ラウンドから走っていたジョブと新しく起動したジョブの**2本同時**に
  `certify_class_unsat.py` へ投入してしまった。両方が同じ `output/cert-5059-2530-x0c1e0/` に
  CNF と DRAT を書き、片方が書いている最中にもう片方が hash を取ったため、
  `proof_sha256` が**空ファイルの hash**（`e3b0c442...`）、`verified=false` という receipt が残った。
- 実際の DRAT（56,168,077 バイト）を現物に対して再検査したところ
  `steps=293830 rup=293830 ... ok=1` で **VERIFIED**（327 秒）。receipt を現物の hash で書き直した。
- 教訓: `certify_class_unsat.py` は同一 (p, size, class) に対して**同時に走らせない**。
  起動前に `Get-CimInstance Win32_Process` で重複を確認する。
- なお `verified=false` を「証明書が不正」と読み替えかけたが、原因は並行書き込みだった。
  receipt の `proof_sha256` が空ファイルの hash になっていることが判別の手がかりになる。
