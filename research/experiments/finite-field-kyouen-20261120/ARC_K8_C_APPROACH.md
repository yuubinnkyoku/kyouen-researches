# k=8 への C 実装：k=7 で完全一致を確認

2026-11-20。`finite-field-kyouen-20261120` の第193部。

前項で「k=8 は Python では不可能」と結論した。本項は**C 実装で
突破を試み、k=7 で完全一致を確認**した。

## 1. 実装

`arc_k8.c`：4円のハッシュ集合を作り、8点部分集合を列挙して
「4円を含むか」を判定する。

```c
// 4円をハッシュ集合に格納
for each circle: for each 4-subset: hinsert(pack4(...))

// 8点部分集合を列挙
for S[0..7]: if (no 4-subset of S is in the hash) arcs++;
```

**最適化**：
- 4円を `uint64` にパック（各点8ビット）
- オープンアドレッシングのハッシュ（2²² エントリ）
- 早期脱出（`!bad` 条件）

## 2. 検証：k=7 で完全一致

同じコードを7点に変更（`arc_k7_check.c`）して q=9 で実行：

```
n=82 b=738
4-circles: 154980
n=82 b=738 total=3801756816 arcs=17003520
```

**`arcs = 17,003,520`** — Python の計算（第180部）と**完全一致**。

**`total = 3,801,756,816 = C(82,7)`** も一致。

**よって C 実装は正しい。**

## 3. q=5 での検証

```
n=26 b=130
4-circles: 1950
n=26 b=130 total=1562275 arcs=0
```

**`arcs = 0`** — `K(5) = 6 < 8` と整合。

**`total = 1,562,275 = C(26,8)`** も一致。

## 4. 計算量

| 対象 | 部分集合数 | 1集合あたりの判定 |
|---|---:|---|
| k=7, q=9 | `C(82,7) = 3.80×10⁹` | 35 個の4部分集合 |
| k=8, q=9 | `C(82,8) = 3.56×10¹⁰` | 70 個の4部分集合 |

**k=8 は k=7 の 9.4倍の集合数、2倍の判定コスト → 約19倍。**

k=7 が C で数分なら、k=8 は**数十分〜数時間**と見込まれる。

## 5. 意義

1. **C 実装が正しいことを k=7 の完全一致で確認した**
   （`arcs = 17,003,520`）。
2. **Python の「20日」という見積もりは言語依存**であり、
   C なら現実的であることを示した。
3. **k=8 の計算が視野に入った**（数十分〜数時間の見込み）。
4. 前項の「3経路すべて不可能」という結論を**部分的に撤回**する
   （プロファイル法は Python では不可能だが、C の直接列挙は可能）。

## 6. 限界

- k=8 の結果は実行中（本項執筆時点）。
- q=11 以降は `C(122,8) = 1.1×10¹¹` で C でも困難。
- メモリ：4円ハッシュは q=9 で 154,980 エントリ（問題なし）。
