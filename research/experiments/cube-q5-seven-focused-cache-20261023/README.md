# 対称根を含む候補表だけで探索を継続する

大きな全候補表を各根から参照する代わりに、その根の立方体等長像を含む行だけを
取り出す。確定候補のラベルと証人は変更しない。未知推定をP/Nへ昇格する処理もない。

## 制限が証明の依存先を落とさない理由

立方体対称群Gと選択根Rに対し、集合族Fを「あるg∈Gでg(R)⊆SとなるS」とする。
S∈Fに1点を加え、その子をhで正規化しても、子は(hg)(R)を含みFに属する。
したがってFは全合法子について閉じている。
N行の正規化P証人も同じ理由でFに残る。正しい完全な証明表をこの族へ制限しても、
R以下の証明を失わない。実装はさらに、保持した全N行のP証人が出力に残ることを検査する。

実際の入力全体は独立未検査の候補表である。フィルタを通したこと自体から勝敗を
採用せず、新たな根が閉じたら通常の全証明書を独立Bareiss検査する。
複数分岐の表を合わせる際は重複keyをまとめ、異なるラベルがあれば拒否する。

| 選択根 | 入力行数 | 保持行数 | cube像数 |
| --- | ---: | ---: | ---: |
| 軸上の対称四石 `{24,169,173,318}` | 138893382 | 192829 | 6 |
| 内側正三角形 `{114,130,214}` | 138893382 | 641828 | 8 |
| 検証用正四面体 `{57,89,257,281}` | 138893382 | 2093401 | 2 |

最初の二つを新しい独立した作業領域の探索対象に選んだ。開始時のnode counterには入力の
counterの最大値113,049,053を使う。これは分岐を合計した総展開数ではない。
後続reportのこのcounterからの差が、その作業領域で新たに行った展開数である。

## 検査

既知3立方の全20根で、元の表と制限後の表から0展開で得る全証明書が完全一致し、
全20証明を独立検査した。重複入力とラベル衝突の拒否も確認した。
raw/gzipを逐次読み直す経路でも、同じ全証明書になった（`regression.json`）。

7立方では検証用四石Pを新しい制限表から0展開で抽出し、337,060局面の独立検査済み
証明書とSHA-256まで一致した（`large-regression.json`）。
この検査は表内の全2,093,401ラベルの独立検査ではない。
圧縮後の12入力から再構築する経路でも、全入力の復元SHAを確認し、この同じ全証明書を
0展開で再現した（`archive-large-regression.json`）。

## privateデータの現所在

以前の全体cache13個を、16,587,503,152 bytesから3,660,734,600 bytesへ可逆圧縮した。
`global-archives.json` に元path・元SHA-256・gzipのpathとSHA-256を記録した。
全展開のbytesとSHA-256が一致した後でrawを除去した。候補行も未知treeも保存している。
以前のexperimentのraw pathは当時の履歴であり、現在はこのinventoryから復元する。
稼働中の根専用の表は別のraw `.memo` と新しい`.hyb`層にあり、これらを参照している。
再生成可能な旧索引10件は除去し、`retired-indices.json`に元hashと依存元を残した。
raw証明書のうちGit内gzipまたは検証済み生成手順と一致する複製、使い終えた検査用の
導出表も除去した（`derived-files-removed.json`）。固有の候補行や証明は失っていない。
prior変更前の追加snapshotは`superseded-checkpoints.json`に可逆保存した。

`filter_archives.py` は一度に一つだけ元rawを一時復元し、それまでの制限表へ合わせる。
全ての巨大rawを同時に復元する必要はない。明示されたinventoryがあれば復元SHAも照合する。
元gzipを変更しない。入力は元の基礎表から依存先順に指定する。

```sh
g++ -O3 -std=c++17 -Wall -Wextra -Werror research/experiments/cube-q5-seven-focused-cache-20261023/filter.cpp -o /tmp/q7-filter-cache
python research/experiments/cube-q5-seven-focused-cache-20261023/regression.py /tmp/q7-filter-cache /tmp/q7-hybrid-v11 /tmp/q7-legacy /tmp/q7-verify-incremental
```

`command.json` は最初のraw入力全リスト。再実行時は各入力の`.gz`を
`filter_archives.py`へ同じ順序で渡す。`run_campaign.py` は先の手動controllerの別版で、
overlayをまだ持たない単一の新基礎表からも開始できる。自動workflowには追加しない。

## 継続時の優先度と終盤

四石根側ではpriorを4から2へ変える試行を加えた（`retune-cross.json`）。
`retune.py`は確定候補行と合法集合・子数・counterを保存し、未知の正のPN/DNだけを
新しい深さpriorへ戻す。元snapshotも保持する。既知3立方のP根・N根を中断して変換し、
再開後の全証明を独立検査した。誤ったpriorの読み込みが拒否されることも確認した。
作業量推定を変える操作であり、P/Nを生成する操作ではない。

`endgame.cpp`は`lazy.cpp`の別版である。残る合法候補が10点以下なら、その後に
置ける点は現在の候補集合の部分集合だけである。禁止された5点集合は石を追加しても
消えないため、新しい合法候補は生まれない。同じ追加部分集合では合法手が同じなので、
最大1,024部分集合を局所memoで完全探索できる。得た結果を通常の証明行へ展開する。
検査器はこの短縮を信用する葉を持たず、引き続き全合法境界を検査する。

子局面の恒久記録も点番号・対称変換番号だけの4 bytesへ縮めた。
親Sと番号(p,g)から子keyはg(S∪{p})として厳密に再構成できる。
完全なkeyは呼び出し中の一時配列に置き、従来の全key照合と子の順序を保つ。
証明書とQ5HYB1/2の保存形式は変えない。

既知3立方20根・中断再開・小さいtree上限・層引継ぎを確認した。
さらに7立方の40終盤で従来df-pnと全勝敗が一致し、両版の全証明を独立検査した。
40件には共存グラフに三角形を持つ6〜10候補の16例を含む。
旧Q5HYB1の明示的な子keyを持つcheckpointからの再開も独立証明で確認した。
外側のnode counterは局所探索1回を1展開と数え、内部評価は`local_states`へ別記する。
従来とのnode数だけの比較を速度向上の証拠にしない。

## 古い未知tree履歴を分離する

さらに容量上限へ近づいたため、旧overlay29層の確定候補部分をrawのまま残し、
当時の未知tree部分だけを別gzipへ分離した。`split-cross-history.json` と
`split-triangle-history.json`に原始header・全体SHA・索引SHA・再構成元を記録した。
全ての元バイトを再構成して照合した後で旧ファイルを除去し、約3.18GBを確保した。

読取用の表は引き続きQ5HYB2で、未知数0とする。候補行・証人・counter・fingerprintは
変えない。索引のrow-offset部分とBloom filterもそのまま残し、実ファイル長の束縛だけを
更新する。最後のfull層と作業中のcheckpointは分離せず、通常のpromotionで再開できる。
原始snapshotは、記録した元header、表の候補行、展開した未知tree tailから完全復元できる。

旧版と新しい局所探索版の両方で、確定行を含む層を分離する前後の継続展開数・
最終全証明書が一致し、独立検査も通った（`regression-history.json`）。
