# K0102 round 2 — feasibility/cost of representing a 9×9 certificate in Lean

Date: 2026-10-17 (local). Workspace: `D:\ghq\github.com\yuubinnkyoku\kyouen-researches`.

## Scope

K0102 asks whether a **concrete** 9×9 certificate can be represented and checked by the Lean kernel alone (not merely whether Lean builds). This report assesses node count, memory, and build time using measured small cases. It does **not** claim 9×9 Lean coverage; K0102 remains open.

## Given data (not recomputed here)

- 9×9 certificate (KYOENC3): **13,457,134 nodes**; 4,630,676 losing + 8,826,458 winning (from `results/all-certificates-check.txt`).
- Raw size ~206 MiB, compressed ~60 MiB (from `research/experiments/certificate-validation/reports/VERIFICATION_REPORT.md`).
- Board has 81 points; rank = 81 − popcount(state).

## Measured Lean baselines

| Case | Nodes | Source size | `.olean` size | Build time | Peak RSS |
|---|---:|---:|---:|---:|---:|
| Cube (3×3×3) | 839 | 14,782 B (`Kyouen/CubeCertData.lean`) | 2,657,976 B | 27.8 s (data 5.0 s + check 18.0 s) | ~440 MB |
| Square 2×2 (new prototype) | 41 | 9,054 B (`Kyouen/SquareCert2x2.lean`) | 356,040 B | 4.1 s | ~440 MB |
| Square 3×3 (attempted) | 9,994 | 1,485,425 B (`Kyouen/SquareCert3x3.lean`, removed) | not produced | >10 min (killed, no completion) | ~443 MB |

Cube numbers are from rebuilding `Kyouen.CubeCertificate` after deleting its `.olean` files. The 2×2 prototype was built successfully; the 3×3 attempt did not finish within 10 minutes.

## Extrapolation to 9×9 (explicitly an estimate)

Using the cube data-only representation as the most compact measured baseline (839 entries, 14,782 B source, 2,657,976 B `.olean`):

- Source: ~17.6 B/node → 13,457,134 × 17.6 ≈ **237 MB** of Lean source.
- Compiled `.olean`: ~3,168 B/node → 13,457,134 × 3,168 ≈ **42.6 GB**.
- Check time if `native_decide` scales like the cube (18 s / 839 nodes ≈ 0.021 s/node): 13,457,134 × 0.021 ≈ **78 hours**. The 3×3 attempt (9,994 nodes, 0.074% of 9×9) already exceeded 10 minutes, so this is optimistic; actual time would likely be much larger.

Memory during such a build is not measured for 9×9, but a 42 GB `.olean` implies RAM requirements far beyond the ~440 MB baseline and beyond typical developer machines.

## Prototype completed

- New module: `Kyouen/SquareCert2x2.lean` (generated by `scratchpad/gen_2x2_lean.py`).
- Represents 41 play-order positions of the 2×2 board.
- Defines `cert`, `certValidBool`, proves `certValidBool = true` by `native_decide`, and proves `empty_board_winning` via `Kyouen.root_winning_of_valid`.
- Build: `lake build Kyouen.SquareCert2x2` succeeds in 4.1 s; project-wide `lake build` still succeeds (22 jobs).

This is a **tiny** case only. It does not cover 3×3 (attempted and not completed within 10 min) and does not approach 9×9.

## Conclusion

Representing the full 9×9 certificate in Lean in the current certificate style is **not feasible** on the measured trajectory: source hundreds of MB, compiled artifact tens of GB, build time days to weeks, and memory far above available. The existing external C++/Rust checker remains the practical verification path. K0102 should stay open; any Lean progress should target smaller bounded cases or split/branch certificates (consistent with KYOENC4's split-DAG design) rather than a single 13.5M-node Lean term.

## Limits / no fabrication

- Node counts and sizes for 9×9 come from repository reports, not from a Lean build.
- Build-time and memory figures for 9×9 are extrapolations from 839-node and 41-node cases plus one incomplete 9,994-node attempt; they are not measurements of a 9×9 Lean build.
- The 3×3 square Lean module was generated but not successfully built; it was removed to keep `lake build` green.
- The 2×2 prototype proves local validity of the embedded 2×2 certificate only; it is not a 9×9 result.
